# markdown database checklist

## T12 markdown database

- [ ] T12 markdown database: `dbspec/` catalog이 선언하는 유한한 저장 문법, orm이 DSN으로 IR executor로서 접속하는 엔진으로서의 flowmark, 같은 행 위의 view. 원인: list·table·detailed 형태는 규칙 없이 demo 사례였고 — body column도, parent도, 관계도, 이력도 없었다 — 계획은 엔진을 orm에 두었으나 엔진은 flowmark에 있었으며, 여러 동작이 하드코딩되어 있었다 (T8.5, T10, T11 후속)
  - 완료 선(polyspec session들과 공유, 2026-10-11): 다음을 모두 만족하면 T12를 완료로 선포한다. (1) 모든 T12 항목이 완료되었다. (2) orm을 기다리는 엔진 지점은 각자 기다리는 orm 항목(`T63`, `T74`, `T89`, `T107`, `T120`과 그 행들이 적은 다른 항목)을 적고, 어떤 stub이나 fallback도 그것을 대신하지 않는다. (3) 모든 항목이 red부터 만들어졌고 main에서 `make test`, `go vet`, `make documents-check`, `make refs-check`가 통과한다. (4) 엔진 전체에 대한 적대 검토 한 번과 Linux·Windows의 T12.13이 통과한다. 그때까지 완료를 막는 결함 말고는 항목을 새로 열지 않으며, 개선은 완료 뒤 목록에 둔다

- [o] T12.1-1 readable-document 판정에 맞춰 spec을 다시 쓴다: `*.flowmark.md` 기준, 주석 없음, file 이름이 key, key와 이름 규칙, field list, 읽을 수 있는 값 형식, 파생 target을 가진 link로서의 외래 key, `<table> <key>` 상세 heading과 그 anchor, walk, 그리고 doc-id header, frontmatter, twin, `dbspec/flowmark.json`의 철회 (T12.1 후속)

- [o] T12.1-2 다른 heading이 가져갈 수 없는 상세 heading: 상세 heading은 `<h> <table> row <key>`이고 anchor는 `<table>-row-<소문자 key>`다. key는 `--`를 담지 않고 `-`로 끝나지 않는다. 상세 anchor는 GitHub의 두 slug 중복 처리(github.com의 counter와 github-slugger의 건너뛰기) 모두에서 비어 있어야 한다. anchor를 가져갈 수 있는 것은 payload heading과 `files` 행의 H1 제목뿐이며, 그렇게 만드는 쓰기는 `CONSTRAINT`다. link는 GitHub식 heading slug를 쓰는 viewer에서 이어진다고 명시한다. 같은 file의 table과 같은 이름의 markdown column 또는 block table에 관한 spec 30 규칙은 그 catalog 검사와 함께 철회한다. 원인: 여러 부모 행 아래 반복되는 block heading이 slug `<table>-1`, `<table>-2`를 가져가는데 이는 상세 heading `<table> 1`, `<table> 2`의 anchor이므로, 정수 key의 block table이 두 부모 행 아래 있는 모든 corpus가 깨진다 (T12.1-1, T12.2.1-1 후속)
  - 완료 기준: spec 10, 20, 30, 50, 100과 계획, 그 twin이 새 heading, anchor, key 규칙을 적고, catalog에 same-file 이름 규칙이 없으며 그 테스트도 함께 제거되고, `go test ./catalog/...`, `make documents-check`, `make refs-check`가 통과한다.
- [o] T12.1-4 상세 anchor는 이름을 든 모든 viewer에서 지켜지고 key는 그 모양을 지킨다: 충돌 검사는 각 heading의 렌더된 inline 텍스트에 대한 두 fold로 한다. F_G(Unicode 범주가 L이나 Nd가 아닌 문자를 지우고, 소문자로 바꾸고, NFKD로 분해하고, 결합 기호를 버리며, ASCII 글자와 숫자만 남긴 것)는 GitHub, GitLab, VS Code를, F_M(소문자로 바꾸고, NFKD로 분해하고, 결합 기호를 버리며, ASCII 글자와 숫자만 남긴 것)은 MkDocs를 다룬다. 두 fold 중 어느 하나에서 충돌하면 충돌이다. 상세 heading이 아닌 heading H는, F = F_G 또는 F = F_M 아래에서 F(H)와 F(A)가 각각의 끝 십진 숫자 run을 뺀 뒤 같으면 상세 heading의 anchor A를 가져간다(명명된 viewer들은 점유되거나 반복된 id를 숫자를 덧붙이거나 끝 숫자를 올려 번호 매기므로, 끝 숫자를 뺀 비교가 모든 번호를 다루며, 그 비용은 상세 heading과 끝 숫자만 다른 payload heading의 거절이다). 두 상세 heading은 anchor가 같을 때에만 충돌하므로 key `P1`과 `P10`은 결코 충돌하지 않는다. payload의 attribute list(앞의 `:`가 있거나 없는 `{…}`)로서 `#<anchor>`로, 또는 `id=` 뒤에 anchor를 그대로나 작은따옴표·큰따옴표 안에 두어 id를 정하는 것과 값이 anchor인 payload HTML의 `id`나 `name`도 충돌한다. 충돌을 새로 만드는 쓰기는 `CONSTRAINT`이며, 다만 중복 key는 `DUPLICATE_KEY`다. viewer 주장은 GitHub, GitLab, VS Code, MkDocs의 anchor 규칙이며, Pandoc은 주장하지 않는다. key는 `--`와 `-_`를 담지 않는다. markdown table의 primary key column은 정수, `bool`, `varchar`, `uuid`, `date` column이며 다른 type은 catalog 오류이고, 음수 정수 key는 `CONSTRAINT`이며, identity는 `i64` key column에만 허용되고, key는 key 모양에 따라 ASCII다. 원인: T12.1-2의 적대 검증이 GitLab, VS Code, Pandoc이 GitHub slug로는 갈리는 payload heading을 상세 anchor로 접는다는 것, `-_`가 강조를 연다는 것, `time`, `datetime`, `decimal`, `f64`, `bytes`와 음수 key는 key 모양을 결코 맞출 수 없다는 것, 충돌하는 쓰기 목록이 불완전하다는 것을 찾았다 (T12.1-2 후속). T12.1-4의 출처 확인은 GitHub과 다르게 접는 것이 Pandoc의 기본 anchor 규칙이고, MkDocs가 악센트 문자를 접는다는 것을 찾았다. GitLab과 VS Code는 GitHub의 문자를 남긴다.
  - 완료 기준: spec 10, 20, 30과 그 twin이 각 규칙을 근거와 함께 적고, catalog가 그 key type을 허용과 거절 사례와 함께 거절하며, `go test ./catalog/...`, `make documents-check`, `make refs-check`가 통과한다.
- [o] T12.1-5 spec이 `document` codec에 필요했던 판정을 적는다: `now`는 `datetime` 기본값에서 현재 시각을 뜻하는 dbspec keyword이며 저장되는 값이 아니고, `now`로 쓰인 시간 값은 그 type이 아니며, 텍스트 `now`는 텍스트다. 저장 순서를 벗어난 table 행은 `format.noncanonical`이고, `parent` 순환은 `parent.cycle`이며 그 file은 저장 순서를 갖지 못한다. 같은 행의 두 번째 상세 section은 `format.block`이다. 제목 token `<선언된 column>\:`은 `CONSTRAINT`다. table cell에서 `|`는 `\|`로만 쓰고 그 밖의 backslash는 더하지 않으며, 읽을 때 `\` 바로 뒤의 `|`는 cell 경계가 아니고 그 `\` 하나를 없앤다. `order`는 논리 column으로, 읽기는 1부터 시작하는 형제 위치로 채우고 쓰기는 형제 묶음마다 정확히 1..m(m은 쓰기 뒤의 묶음 크기)을 받는다. codec은 행에서 저장 순서를 계산하며 정렬되지 않은 입력을 거절하지 않는다. 진단의 column은 그 규칙이 가리키는 요소의 1부터 시작하는 code point column이다. 상태기계가 있는 table의 `list` 저장은 `checkbox`를 하나 이상 선언하고, 그 상태 column은 non-null이다. dangling 참조는 쓰인 target을 유지한다. 값은 setext heading을 담지 않으며, fence나 CommonMark type 1–5의 HTML block을 연 채로 두는 값은 뒤에 요소가 오면 `CONSTRAINT`다. 두 행이 함께 가진 key를 가리키는 table `parent` cell은 `format.block`이다. 원인: T12.2.3 codec의 적대 검증이 규칙 없이 내린 각 판단을 찾았다 (T12.2.3, T12.1-3 후속)

  - 완료 기준: spec 10과 그 twin이 그 판정을 근거와 함께 적고, `make documents-check`와 `make refs-check`가 통과한다.
- [o] T12.1-8 spec이 다시 짠 `files` codec에 필요했던 읽기 규칙을 적는다: 뒤에 요소가 오기 전에 CommonMark type 1–5의 HTML block을 열어 둔 값을 담은 file은 쓰기에서 `CONSTRAINT`이듯 읽기에서 `format.block`이다. 읽은 형태를 쓰기 규칙이 다시 만들 수 없는 제목(예: `# a\\#`)은 `format.block`이다. 홀로 쓰인 CR은 줄 끝이며 `format.noncanonical`이다. 한 줄 자리 규칙의 공백은 space와 tab이다. 원인: T12.2.2-1 codec이 규칙 없이 이것들을 하나씩 골라야 했다 (T12.2.2-1 후속)

- [o] T12.1-9 단일 줄 자리의 양 끝에 있는 보이지 않는 문자는 거절한다. 그런 문자는 글리프 없이 그려지므로 독자는 볼 수 없고, 이름 붙은 viewer들은 그런 문자를 서로 다른 집합으로 떼어내기 때문이다. 보이지 않는 문자는 U+1680을 뺀 Unicode White_Space 속성의 문자, 제어 문자(Cc), Prepended_Concatenation_Mark를 뺀 형식 문자(Cf, U+FEFF 포함), Default_Ignorable_Code_Point이며 Unicode 17.0.0 기준이다. spec 10이 근거와 함께 이를 적는다 (T12.1-8 후속)
